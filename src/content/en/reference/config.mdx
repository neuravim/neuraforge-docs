# Configuration Reference

> This public reference covers user-facing configuration. Detailed internal schemas are kept in the internal documentation.

## Minimal project config

```yaml
project: my-project
provider: claude-code
mode: standard
lang: en
```

## Common keys

| Key | Purpose |
|---|---|
| `project` | Names the project for generated artifacts and tracking |
| `provider` | Chooses the default AI provider |
| `mode` | Selects `flash`, `standard`, or `enterprise` |
| `lang` | Chooses the artifact language |
| `rules` | Points to team rules that guide work |
| `memory` | Enables or constrains contextual memory |

## Provider preferences

NeuraForge can work with multiple providers. Public configuration should stay focused on which provider is preferred and whether a team uses local, cloud or enterprise-managed AI access.

```yaml
provider: claude-code
```

For provider-specific authentication and installation, see the provider guides.

## Workflow mode

```yaml
mode: standard
```

- `flash`: small, low-risk changes.
- `standard`: normal feature work.
- `enterprise`: sensitive, regulated or production-critical changes.

## Rules and templates

```yaml
rules:
  - .neuraforge/rules/coding-standards.md
```

Rules and templates help teams make expectations explicit. Keep detailed internal process rules in private engineering docs when they describe implementation internals.

## Memory

```yaml
memory:
  enabled: true
```

Memory helps NeuraForge reuse durable project context. Treat it as guidance, not as the source of truth.

## Enterprise standards

Organizations can define shared standards for mode, providers, approvals, security expectations, tests and documentation. The exact schema should be managed internally by the platform or engineering enablement team.

## CLI helpers

```bash
neuraforge config show
neuraforge config set mode enterprise
neuraforge config get provider
```

## Public/private boundary

Public docs intentionally avoid exposing:

- full internal schemas;
- prompt assembly details;
- hook contracts;
- orchestration internals;
- provider-routing algorithms;
- quality-gate thresholds.

If you need those details, use the internal technical documentation.
