# Agent Profiles & Domain Playbooks

> Agent profiles and domain playbooks let teams adapt NeuraForge to specialized work without exposing or changing the core orchestration engine.

## Why use profiles and playbooks?

Different domains need different judgment. A payment feature, a GDPR remediation task and a WildFly to Spring Boot migration should not be handled with identical assumptions.

NeuraForge keeps the same controlled delivery model while letting teams add domain context:

- terminology;
- risk areas;
- expected artifacts;
- validation expectations;
- documentation requirements;
- rollout and rollback concerns.

## Agent profiles

An agent profile specializes the behavior of the built-in workflow for a domain. It does not create a new product architecture; it guides the existing roles with the right context.

Examples:

- legacy Java migration;
- regulated healthcare workflow;
- fintech security review;
- data-platform change management;
- frontend accessibility review.

## Domain playbooks

A domain playbook packages reusable guidance for a class of work.

A migration playbook, for example, can tell NeuraForge to focus on:

- current-state inventory;
- compatibility risks;
- incremental migration strategy;
- behavior preservation;
- test coverage;
- rollback planning;
- operational documentation.

The internal file layout, manifest schema, hook contracts and executable helper scripts are intentionally kept out of the public documentation. They belong in internal engineering docs.

## Example: WildFly to Spring Boot

For a WildFly to Spring Boot migration, a public playbook should describe the outcome, not the internal implementation contract.

A good public request is:

```bash
neuraforge enterprise "Migrate this WildFly application to Spring Boot" --profile wildfly-to-spring-boot
```

The workflow should help the team:

1. inventory the legacy application;
2. identify Java EE dependencies and runtime assumptions;
3. define an incremental migration path;
4. preserve behavior before modernization;
5. validate security and transaction parity;
6. prepare rollout, rollback and support documentation.

## Public vs internal content

Keep public docs focused on:

- what the playbook is for;
- when to use it;
- what outcomes it produces;
- what kind of evidence reviewers should expect.

Keep internal docs focused on:

- exact profile definitions;
- artifact schemas;
- hook events;
- scripts;
- validation internals;
- implementation details.
