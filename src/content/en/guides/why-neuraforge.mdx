# Why NeuraForge

> A practical guide to using NeuraForge, understanding what it solves, and deciding when a controlled AI delivery workflow is worth the extra structure.

## In one sentence

NeuraForge helps product and engineering organizations turn a functional request into a verified delivery, with specialized AI agents working inside a controlled workflow.

Not another chatbot. Not a folder of prompts to maintain. A CLI tool that fits into an existing repository and brings order to agent work.

## The problem: agent output is not delivery

AI agents can generate code. In an organization, the harder question is control:

- what was requested;
- what was decided;
- whether the code actually changed;
- whether the result is more than a local demo;
- whether quality, security and acceptance criteria were checked;
- whether the trail is clear enough to review later;
- how much time the team spends coordinating analysis, development, review, documentation and follow-up.

NeuraForge sits between product intent and delivery. It does not replace the team. It reduces the time wasted manually steering a network of agents that can otherwise drift.

## Quick usage

```bash
npm install -g @neuravim/neuraforge
cd my-project
neuraforge init
neuraforge flash "Fix pagination on /users"
```

For a more structured feature:

```bash
neuraforge standard "Add CSV export with tests"
```

For sensitive work, with stricter documentation and validation:

```bash
neuraforge enterprise "Migrate authentication to OIDC with a runbook"
```

Then track progress and cost:

```bash
neuraforge status
neuraforge metrics
neuraforge trace <feature>
```

## Three levels, not one hammer

- `flash` is for fixes and small changes. The team moves fast but keeps a trail.
- `standard` is for normal product features. Analysis, planning, implementation and review stay attached to the same feature.
- `enterprise` is for sensitive work: security, compliance, migration, operating documentation and human approval.

This avoids a common trap: forcing a heavy workflow onto every ticket, or treating a critical migration like a simple code generation prompt.

### Standard vs Enterprise: the real difference

The difference is not just the number of agents. **Standard** is about controlled feature delivery: a product request becomes a real change with analysis, plan, tests, security review and QA. It is the right level when the team wants to move fast without losing the link between intent, acceptance criteria and modified code.

**Enterprise** is about governed delivery: the change must stand in front of a CTO, a security team, operations or business stakeholders. The workflow adds operational documentation, runbooks, human approval, auditability and production readiness. It is the natural level for a WildFly to Spring Boot migration, authentication change, compliance constraint or critical system.

In short: Standard prevents fragile features. Enterprise prevents critical changes that cannot be defended in production.

## What changes in practice

### Delivery control

- Requests, decisions and outputs stay connected.
- Responsibilities are separated across analysis, planning, code, security, QA and documentation.
- Gates reduce the risk of mistaking a convincing answer for a finished deliverable.
- Existing repositories can adopt the workflow without becoming demo-only sandboxes.

### Product clarity

- Acceptance criteria remain visible throughout the workflow.
- Deliverables are attached to a feature, not lost in a chat thread.
- Tradeoffs are easier to review later.
- Each request can use the right level of rigor without slowing down every small fix.

### Operational visibility

- Progress, blockers and cost signals are easier to inspect.
- AI adoption becomes less improvised and easier to standardize.
- Hidden coordination cost is reduced: repeated context setting, unclear reviews, forgotten documentation and late rework.
- Sensitive changes can carry the documentation and approvals expected for production work.

NeuraForge does not sell magic. It targets waste: context repeated again and again, reviews redone because criteria were vague, agents burning tokens on oversized prompts, and features that look done but come back two days later.

## Featured use case: migrating WildFly to Spring Boot

A concrete example for large organizations: migrating WildFly/JBoss or Java EE applications to Spring Boot.

The pattern is familiar: critical applications, historical dependencies, application servers that are expensive to maintain, incomplete tests, scattered documentation, and pressure to modernize for cloud and security programs.

NeuraForge is useful here because the job is not just "convert code". The team needs to preserve business behavior, identify risks, create a migration plan, change the right files, replace server-based tests with Spring Boot tests, verify endpoints and document what changed.

A typical workflow:

```bash
neuraforge enterprise "Migrate the customer module from WildFly to Spring Boot with tests, smoke tests and an operating runbook"
```

The value is practical: modernization can move forward in verified increments instead of forcing a full-platform rewrite. That means less operational debt, less dependency on a legacy runtime, and less time spent reconstructing technical context for every migration.

## NeuraForge vs BMAD

BMAD made multi-agent work easier to reason about. NeuraForge starts from a different question: how do you make that logic usable in a real repository, with less friction and more control over delivery?

| Topic | BMAD | NeuraForge |
|---|---|---|
| Main intent | Structure reasoning and preparation | Control execution through verified delivery |
| Startup | More framing before code | Fast initialization, then the right mode for the risk |
| Working mode | Heavier workflow by default | Flash, standard or enterprise depending on the risk |
| Brownfield usage | Often needs more manual adaptation | Designed to work inside existing projects |
| Agents | Strong role and document logic | Roles tied to verifiable outputs |
| Quality | Depends heavily on execution discipline | Built-in gates block weak deliveries |
| AI cost | Can consume a lot of context | Routing, scopes and compression reduce waste |
| Visibility | Good thinking support | Clearer progress, blockers and cost signals |
| Product delivery | Useful for framing | Useful for tracking a feature until usable output |

## The point

NeuraForge does not need to be sold as a revolution. Technical teams usually see the issue quickly: agents can produce volume without producing a controlled delivery.

NeuraForge reduces that gap.

It gives organizations a cleaner way to use AI in software delivery: simple enough to adopt, strict enough to avoid false positives, and traceable enough to defend internally.
