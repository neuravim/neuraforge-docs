# Agent Profiles & Domain Playbooks

> Les agent profiles et domain playbooks permettent d'adapter NeuraForge à un domaine spécialisé sans exposer ni modifier le moteur d'orchestration.

## Pourquoi utiliser des profiles et playbooks ?

Tous les domaines ne demandent pas le même jugement. Une fonctionnalité paiement, une correction GDPR et une migration WildFly vers Spring Boot ne doivent pas être traitées avec les mêmes hypothèses.

NeuraForge garde le même modèle de livraison contrôlée tout en ajoutant du contexte métier :

- terminologie ;
- zones de risque ;
- artefacts attendus ;
- attentes de validation ;
- exigences documentaires ;
- rollout et rollback.

## Agent profiles

Un agent profile spécialise le comportement du workflow intégré pour un domaine. Il ne crée pas une nouvelle architecture produit ; il guide les rôles existants avec le bon contexte.

Exemples :

- migration Java legacy ;
- workflow santé réglementé ;
- revue sécurité fintech ;
- changement data-platform ;
- revue accessibilité frontend.

## Domain playbooks

Un domain playbook package du guidage réutilisable pour une classe de travaux.

Un playbook de migration peut par exemple orienter NeuraForge vers :

- inventaire de l'existant ;
- risques de compatibilité ;
- stratégie de migration incrémentale ;
- préservation du comportement ;
- couverture de tests ;
- plan de rollback ;
- documentation opérationnelle.

Le layout interne des fichiers, le schéma du manifest, les contrats de hooks et les scripts d'aide exécutables restent volontairement hors de la documentation publique. Ils appartiennent à la documentation d'ingénierie interne.

## Exemple : WildFly vers Spring Boot

Pour une migration WildFly vers Spring Boot, la doc publique doit décrire le résultat attendu, pas le contrat d'implémentation interne.

Une demande publique correcte :

```bash
neuraforge enterprise "Migrate this WildFly application to Spring Boot" --profile wildfly-to-spring-boot
```

Le workflow doit aider l'équipe à :

1. inventorier l'application legacy ;
2. identifier les dépendances Java EE et hypothèses runtime ;
3. définir une trajectoire de migration incrémentale ;
4. préserver le comportement avant modernisation ;
5. valider la sécurité et la parité transactionnelle ;
6. préparer rollout, rollback et documentation support.

## Public vs interne

Gardez en public :

- l'objectif du playbook ;
- les cas d'usage ;
- les résultats produits ;
- les preuves attendues par les reviewers.

Gardez en interne :

- définitions exactes de profiles ;
- schémas d'artefacts ;
- événements hooks ;
- scripts ;
- détails de validation ;
- détails d'implémentation.
