# Pourquoi NeuraForge

> Un guide concret pour utiliser NeuraForge, comprendre le problème qu'il résout et décider quand un workflow IA contrôlé mérite plus de structure.

## En une phrase

NeuraForge aide les organisations produit et engineering à passer d'une demande fonctionnelle à une livraison vérifiée, avec des agents IA spécialisés qui travaillent dans un cadre contrôlé.

Pas un chatbot de plus. Pas un dossier de prompts à maintenir. Un outil CLI qui s'intègre dans un repo existant et qui met de l'ordre dans le travail des agents.

## Le problème : une sortie d'agent n'est pas une livraison

Les agents IA savent produire du code. Le vrai sujet, pour une organisation, c'est le contrôle :

- savoir ce qui a été demandé ;
- comprendre ce qui a été décidé ;
- vérifier que le code a réellement changé ;
- éviter les livraisons "démo locale" ;
- vérifier qualité, sécurité et critères d'acceptation ;
- garder une trace exploitable pour relire les décisions ;
- réduire le temps passé à coordonner analyse, dev, review, documentation et relance.

NeuraForge se place à cet endroit : entre l'intention produit et le delivery. Il ne remplace pas l'équipe. Il évite qu'elle perde du temps à piloter manuellement un réseau d'agents qui part dans tous les sens.

## Utilisation rapide

```bash
npm install -g @neuravim/neuraforge
cd mon-projet
neuraforge init
neuraforge flash "Corriger le bug de pagination sur /users"
```

Pour une feature plus structurante :

```bash
neuraforge standard "Ajouter un export CSV avec tests"
```

Pour un sujet sensible, avec documentation et validation plus stricte :

```bash
neuraforge enterprise "Migrer l'authentification vers OIDC avec runbook"
```

Vous pouvez ensuite suivre l'avancement et les coûts :

```bash
neuraforge status
neuraforge metrics
neuraforge trace <feature>
```

## Trois niveaux, pas un seul marteau

- `flash` convient aux corrections et petites évolutions. L'équipe va vite, mais garde une trace.
- `standard` convient aux features produit classiques. Analyse, plan, implémentation et review restent liés à la même feature.
- `enterprise` convient aux sujets sensibles : sécurité, conformité, migration, documentation d'exploitation, validation humaine.

Ce découpage évite un piège fréquent : appliquer un workflow lourd à chaque ticket, ou à l'inverse traiter une migration critique comme un simple prompt de génération de code.

## Ce que NeuraForge change dans la pratique

### Contrôle du delivery

- Les demandes, décisions et sorties restent connectées.
- Les responsabilités sont séparées : analyse, plan, code, sécurité, QA, documentation.
- Les gates limitent le risque de confondre "réponse convaincante" et "livrable terminé".
- Les projets existants peuvent adopter le workflow sans devenir des prototypes locaux.

### Clarté produit

- Les critères d'acceptation restent visibles pendant le workflow.
- Les livrables sont attachés à une feature, pas perdus dans une conversation.
- Les arbitrages sont plus faciles à relire.
- Chaque demande peut recevoir le bon niveau de rigueur sans ralentir les petites corrections.

### Visibilité opérationnelle

- L'avancement, les blocages et les signaux de coût sont plus faciles à inspecter.
- L'adoption IA devient moins artisanale et plus standardisable.
- Le coût caché de coordination diminue : contexte répété, reviews floues, documentation oubliée, corrections tardives.
- Les changements sensibles peuvent porter la documentation et les validations attendues pour une livraison production.

NeuraForge ne promet pas de magie. Il attaque surtout les coûts invisibles : le contexte répété, les reviews refaites parce que les critères étaient flous, les agents payés à tourner sur des prompts trop longs, et les features qui semblent finies puis reviennent deux jours plus tard.

## Cas mis en vedette : migrer WildFly vers Spring Boot

Un exemple parlant pour les grandes organisations : la migration d'applications WildFly/JBoss ou Java EE vers Spring Boot.

Le schéma est connu : applications critiques, dépendances historiques, serveurs d'application coûteux à maintenir, tests parfois incomplets, documentation dispersée, pression de modernisation cloud et sécurité.

NeuraForge est intéressant ici parce que le problème n'est pas seulement de "convertir du code". Il faut garder le comportement métier, identifier les risques, produire un plan de migration, modifier les bons fichiers, remplacer les tests serveur par des tests Spring Boot, vérifier les endpoints et documenter ce qui a changé.

Un workflow typique :

```bash
neuraforge enterprise "Migrer le module clients WildFly vers Spring Boot avec tests, smoke tests et runbook d'exploitation"
```

La valeur est concrète : la modernisation avance par incréments vérifiables au lieu de demander une réécriture complète de plateforme. Cela signifie moins de dette d'exploitation, moins de dépendance à un runtime legacy et moins de temps passé à reconstituer le contexte technique à chaque migration.

## NeuraForge vs BMAD

BMAD a popularisé une façon structurée de penser le travail multi-agents. NeuraForge part d'une préoccupation différente : comment rendre cette logique utilisable dans un repo réel, avec moins de friction et plus de contrôle sur la livraison.

| Sujet | BMAD | NeuraForge |
|---|---|---|
| Intention principale | Structurer le raisonnement et la préparation | Encadrer l'exécution jusqu'au livrable vérifié |
| Démarrage | Plus de cadrage avant d'arriver au code | Initialisation rapide puis choix du mode adapté |
| Mode de travail | Workflow plutôt lourd par défaut | Flash, standard ou enterprise selon le risque |
| Usage brownfield | Demande souvent plus d'adaptation | Pensé pour travailler dans un projet existant |
| Agents | Forte logique de rôles et de documents | Rôles reliés à des sorties vérifiables |
| Qualité | Dépend beaucoup de la discipline d'exécution | Gates intégrés pour bloquer les livraisons faibles |
| Coûts IA | Peut consommer beaucoup de contexte | Routage, scopes et compression pour limiter le gaspillage |
| Visibilité | Bon support de réflexion | Signaux plus clairs sur avancement, blocages et coûts |
| Livraison produit | Utile pour cadrer | Utile pour suivre une feature jusqu'à une sortie exploitable |

## Le point important

NeuraForge n'a pas besoin d'être vendu comme une révolution. Les équipes techniques voient assez vite le problème : les agents seuls produisent du volume, pas forcément une livraison maîtrisée.

NeuraForge sert à réduire cet écart.

Il donne aux organisations un cadre plus propre pour utiliser l'IA dans le delivery logiciel : assez simple pour être adopté, assez strict pour éviter les faux positifs, assez traçable pour être défendable en interne.
