# Gouvernance mémoire

> La mémoire n'est utile que si les agents savent ce qu'elle signifie, si elle est fraîche, et quand ils ont le droit de lui faire confiance. NeuraForge rend tout ça explicite avec une gouvernance mémoire par scopes.

**Ce que vous allez apprendre :**
- Les quatre scopes mémoire : task, session, project, user
- Comment la précédence résout les conflits
- Les politiques de lecture/écriture et les cycles de vie
- Comment la gouvernance mémoire est injectée dans les prompts agents
- Comment configurer la mémoire proprement dans `.neuraforge/neuraforge.config.yaml`

## Pourquoi une mémoire par scopes ?

Les agents IA ont besoin de contexte, mais le contexte peut devenir obsolète. NeuraForge traite la mémoire comme des **indices contextuels, pas comme une source de vérité**. Le repository, les fichiers actuels, les tests et la demande explicite de l'utilisateur gagnent toujours.

La mémoire par scopes donne un contrat clair à chaque agent :

| Scope | Cycle de vie | Contenu typique | Comportement par défaut |
|---|---|---|---|
| `task` | Éphémère | Objectif courant, contraintes, décisions temporaires | Toujours lue, écriture automatique |
| `session` | Session | Progression workflow, handoffs, contexte court terme | Lecture contextuelle, écriture automatique |
| `project` | Persistant | Conventions projet, architecture, pratiques d'équipe | Lecture contextuelle, écriture suggérée, revalidation avant usage |
| `user` | Persistant | Préférences utilisateur et préférences stables | Lecture contextuelle, écriture suggérée |

## Précédence par défaut

Quand deux scopes se contredisent, NeuraForge utilise cette précédence :

```text
task > session > project > user
```

Donc la tâche courante gagne sur la session, la session gagne sur la mémoire projet persistante, et la mémoire projet gagne sur les préférences utilisateur générales.

Exemple : si la mémoire utilisateur dit « préférer Jest », que la mémoire projet dit « ce repo utilise Vitest », et que la tâche courante demande « pas de nouveaux tests », la tâche gagne.

## Injection dans les prompts

Quand `memory.enabled` vaut true, chaque prompt agent reçoit une section comme celle-ci :

```text
--- Memory Governance ---
Workflow Mode: standard
Memory is governed by explicit scopes. Treat memory as contextual hints, not source of truth.
Scope precedence: task > session > project > user
task: read=always, write=automatic, lifecycle=ephemeral, maxSize=small, sensitivity=low, summarization=none
session: read=contextual, write=automatic, lifecycle=session, maxSize=large, sensitivity=medium, summarization=on_close
project: read=contextual, write=suggested, lifecycle=persistent, maxSize=medium, sensitivity=medium, summarization=periodic, revalidateBeforeUse=true
user: read=contextual, write=suggested, lifecycle=persistent, maxSize=small, sensitivity=medium, summarization=on_limit
```

Ce n'est pas juste de la documentation. Cela modifie les instructions vues par les agents pendant l'analyse, la planification, le code, la QA et DocOps.

## Configuration

La gouvernance mémoire est active par défaut. Vous pouvez la rendre explicite dans `.neuraforge/neuraforge.config.yaml` :

```yaml
memory:
  enabled: true
  scopePrecedence: [task, session, project, user]
  scopes:
    task:
      enabled: true
      lifecycle: ephemeral
      readPolicy: always
      writePolicy: automatic
      maxSize: small
      sensitivity: low
      summarization: none
    session:
      enabled: true
      lifecycle: session
      readPolicy: contextual
      writePolicy: automatic
      maxSize: large
      sensitivity: medium
      summarization: on_close
    project:
      enabled: true
      lifecycle: persistent
      readPolicy: contextual
      writePolicy: suggested
      maxSize: medium
      sensitivity: medium
      summarization: periodic
      revalidateBeforeUse: true
    user:
      enabled: true
      lifecycle: persistent
      readPolicy: contextual
      writePolicy: suggested
      maxSize: small
      sensitivity: medium
      summarization: on_limit
```

## Référence des politiques

### Read policy

| Valeur | Signification |
|---|---|
| `never` | Le scope ne doit pas être lu. |
| `explicit` | Lecture seulement quand elle est demandée explicitement. |
| `contextual` | Lecture quand c'est pertinent pour la tâche courante. |
| `always` | Toujours inclure/utiliser ce scope. |

### Write policy

| Valeur | Signification |
|---|---|
| `never` | Ne jamais écrire dans ce scope. |
| `manual` | Écriture contrôlée par un humain uniquement. |
| `suggested` | L'agent peut suggérer une écriture, mais ne doit pas persister silencieusement. |
| `automatic` | L'agent peut écrire automatiquement quand c'est approprié. |

### Lifecycle

| Valeur | Signification |
|---|---|
| `ephemeral` | Vit seulement pendant la tâche courante. |
| `session` | Vit pendant le workflow/la session courante. |
| `ttl` | Expire après un TTL configuré. |
| `persistent` | Durable entre sessions/projets, selon les règles du scope. |

### Summarization

| Valeur | Signification |
|---|---|
| `none` | Pas de résumé. |
| `periodic` | Résumer régulièrement. |
| `on_limit` | Résumer quand le scope atteint sa limite de taille. |
| `on_close` | Résumer à la fermeture de session. |

## Défauts sûrs

Les valeurs par défaut NeuraForge sont prudentes :

- `project.revalidateBeforeUse: true` empêche des notes projet obsolètes d'écraser la réalité.
- Les écritures user et project sont `suggested`, pas automatiques.
- La mémoire task est low-sensitivity et éphémère.
- La mémoire session peut être automatique, car elle est courte durée.

## Patterns courants

### Désactiver la mémoire user pour un projet sensible

```yaml
memory:
  scopes:
    user:
      enabled: false
```

### Forcer la mémoire projet en explicite uniquement

```yaml
memory:
  scopes:
    project:
      readPolicy: explicit
      writePolicy: manual
```

### Ajouter une rétention TTL à la mémoire session

```yaml
memory:
  scopes:
    session:
      lifecycle: ttl
      retention:
        ttlMs: 86400000
        maxEntries: 200
```
